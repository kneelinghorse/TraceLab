Mission R2.2: Markdown Ingestion Service Design Specification
1. Executive Briefing: Recommended Architecture
Primary Recommendation: This report recommends the development of a new, standalone Node.js ingestion service. This service will be architected as a decoupled, event-driven pipeline centered on the unified ecosystem, utilizing remark for Markdown parsing. File discovery will be managed by chokidar for high-fidelity file system monitoring, with a message queue providing resilient task processing.

Executive Justification: The mission's primary constraint—preserving heading hierarchy for chunking—is fundamentally an Abstract Syntax Tree (AST) manipulation problem, not an HTML rendering task. The unified/remark stack is explicitly designed for AST-first transformation, providing a robust plugin architecture that is superior to the fragmented and HTML-centric tooling available in the Python ecosystem. This architectural choice directly enables a more accurate, maintainable, and resilient chunking algorithm, which is the cornerstone of high-quality Retrieval-Augmented Generation (RAG) retrieval.

High-Level Architectural Model: The system will be composed of the following decoupled components:

File System Watcher (chokidar): Monitors the cmos/missions/research/ directory for file creation, modification, and deletion events.

Message Queue (e.g., RabbitMQ/SQS): Decouples file discovery from processing, providing resilience, retry logic, and back-pressure for batch operations.

Ingestion Worker (Node.js/unified): The core service that consumes tasks from the queue and executes the Parse-Chunk-Embed-Index workflow.

Semantic Cache (Qdrant): The existing target vector store.

Telemetry Collector (OpenTelemetry): Gathers operational metrics for monitoring pipeline health.

Control Plane (CLI/API): Interfaces for triggering batch backfilling of the corpus and managing on-demand ingestion tasks.

The initial search for a single "markdown parser" is a misleading simplification. The investigation reveals that a robust solution is not a single tool but a "pipeline" or "ecosystem." The unified project provides an "interface for parsing, inspecting, transforming, and serializing content through syntax trees". remark is the specific ecosystem for the Markdown AST (mdast).

By adopting this model, the required custom chunking logic will not be a complex, external script that iterates over a static tree. Instead, it will be implemented as a simple, declarative remark plugin that integrates directly into the parsing stream. This is a fundamentally more cohesive and maintainable architectural pattern that directly addresses the mission's requirements.

2. Markdown Parser Ecosystem Analysis
2.1 The Core Requirement: AST Manipulation vs. HTML Rendering
The success of this mission is contingent on extracting structured metadata (YAML front matter, heading hierarchy) and performing chunking based on document structure. This requires a parser that provides first-class, "lossless" access to a structured, traversable Abstract Syntax Tree (AST).

A majority of traditional Markdown parsers, including markdown-it and Python-Markdown, are "HTML-first." Their primary objective is to render HTML. AST access is often a secondary, non-standardized, or lossy feature.

The unified ecosystem, through its remark processor, is "AST-first." It parses Markdown into a well-defined mdast (Markdown Abstract Syntax Tree). This mdast is explicitly designed to be traversed, inspected, and transformed by plugins. The resulting tree can then be "stringified" back to Markdown or, via remark-rehype, transformed into an HTML AST (hast) for rendering. For the purposes of data ingestion, this mdast is the final artifact required.

2.2 Evaluation of the Python Stack
mistletoe: A strong contender, mistletoe is pure Python, CommonMark compliant, fast, and provides a clear AST. It also includes native support for FrontMatter tokens, which is a significant advantage. However, its AST is a custom mistletoe specification, not the cross-language mdast standard, and its plugin ecosystem is less mature.

markdown-it-py: A Python port of the popular Node.js library. It is extensible and CommonMark compliant, but it shares the "HTML-first" philosophy. Its "AST" is a linear list of "tokens," not a true hierarchical tree, making structural analysis (e.g., "find all paragraphs under this heading") complex.

markdown-it-pyrs: A Rust-based, high-performance variant of markdown-it-py, offering a >20x speed increase. This performance is compelling but comes with a critical, disqualifying trade-off: because it vendors compiled Rust code, Python-based plugins cannot be dynamically added. This makes it unsuitable for the mission, which requires a custom chunking plugin.

Python-Markdown & python-frontmatter: This is the legacy approach. The parser is mature but not CommonMark compliant, and its extension system is considered "awkward". It also requires a separate, "bolted-on" library (python-frontmatter) to handle YAML metadata, a task that mistletoe and remark handle integratedly.

2.3 Evaluation of the Node.js Stack
unified/remark: This ecosystem is purpose-built for AST manipulation. The architecture is modular and provides all necessary components:

unified: The core pipeline engine.

remark-parse: The high-fidelity Markdown-to-mdast parser.

remark-frontmatter: A standard plugin to parse YAML front matter and attach it to the mdast's root data attribute.

unist-util-visit: A standard utility for traversing the mdast tree. This utility is the key to implementing the custom chunking algorithm.

markdown-it (Node.js): As with its Python counterpart, this library is "HTML-first" and does not provide a clean, traversable AST suitable for structural analysis.

2.5 Final Recommendation: unified/remark (Node.js)
The unified/remark ecosystem is the only one investigated that treats Markdown-to-AST transformation as its primary, first-class function. Its standardized mdast specification and rich plugin ecosystem (e.g., remark-frontmatter) provide the exact tools required to implement the hierarchical chunking algorithm as a clean, maintainable, and declarative plugin. This approach avoids the fragmentation of the Python stack (e.g., parser + frontmatter-lib + custom-walker) and the critical extensibility-dead-end of high-performance options like markdown-it-pyrs.

3. A Hierarchical Chunking Strategy for RAG
3.1 Rejecting Naive Chunking Strategies
The quality of the semantic cache is dictated by the quality of its chunks. Naive chunking strategies are a primary source of poor RAG performance.

Fixed-Size Chunking: This is the most basic and least effective approach. It arbitrarily splits text, breaking code blocks, table rows, and semantic concepts. This leads to "legally impressive nonsense" where context is severed, and retrieved chunks are unusable.

Recursive Character Chunking: This is the default for many frameworks like LangChain and is marginally better. However, it still views the document as a flat string, splitting on a hierarchy of separators (e.g., \n\n, then \n, then ). This will still split a code block from its preceding explanatory paragraph or break a complex list.

MarkdownHeaderTextSplitter (LangChain): This tool is based on the correct principle (splitting by headers) but has a flawed implementation. Analysis of user complaints and its implementation reveals it is regex-based, not AST-based. This leads to two critical failures:

It strips meaningful whitespace (newlines, indentation) to "clean" the text, which corrupts the formatting of code blocks, poetry, and lists.

It is fragile and cannot correctly parse complex nested structures that a true AST-based parser handles natively.

3.2 Proposed: An mdast-Based Hierarchical Chunking Algorithm
A custom remark plugin will be developed to traverse the mdast. This algorithm ensures "chunk coherence" (an explicit evaluation criterion) by respecting the document's semantic structure.

Algorithm Steps:

Parse: The file is parsed into an mdast using remark-parse and remark-frontmatter. The front matter data is stored on the root node.

Initialize: The plugin initializes an empty chunks array and a header_trail stack (e.g., ``).

Traverse: The plugin uses unist-util-visit to perform a depth-first traversal of the mdast nodes.

Identify Semantic Sections:

When the visitor enters a heading node, its text content is pushed onto the header_trail stack (e.g., ``).

When the visitor exits a heading node, its corresponding entry is popped from the stack.

Identify Atomic Blocks: The visitor will specifically look for "atomic" node types that must not be split: code (fenced code blocks) and table.

code: The entire block is treated as one chunk. Its content (the raw, whitespace-preserved code) is stored. A content_type (e.g., code_python) is extracted from the fence info.

table: The entire table is treated as one chunk. Its content is the raw Markdown text of the table, and content_type is set to table_markdown.

Splitting code or tables renders them unusable for RAG. If an atomic block exceeds the target token limit, it is indexed as a single, oversized chunk, and a chunk_oversized: true flag is added to its metadata. This allows downstream agents to decide whether to load this large chunk into context.

Chunk Text Blocks: For all other content nodes (paragraph, list, blockquote), their raw text is aggregated into a single block.

Final Split (Recursive Fallback): After a full semantic section of text is aggregated (e.g., all paragraphs and lists under a ### heading), this aggregated text block is passed to a secondary splitter, such as a RecursiveCharacterTextSplitter, to break it down to the final target token size (e.g., 512 tokens). This provides the optimal balance: high-level semantic boundaries (from the AST) and low-level token compliance.

3.3 Context Preservation: The Key to RAG
As identified in and, retrieval context is lost if chunks are isolated. The proposed data model solves this: each chunk, whether atomic or text, will be stored with a payload containing:

Full Front Matter: The entire YAML front matter is duplicated on every chunk from that document.

Heading Trail: The current state of the header_trail stack (e.g., ``).

When a single chunk is retrieved via semantic search, the agent will have the full document context (from the front matter) and the full sectional context (from the heading trail) available for generation.

4. Qdrant Data Model and Integration
4.1 The Parent-Child Data Model
A simple data model of "one chunk = one vector" is inefficient, as small chunks lack the broader context required for high-quality RAG answers.

This design will implement a "Parent Document" retrieval strategy. Both the full, raw parent document and the small, embeddable child chunks will be stored. Agents will search against the semantically-rich small chunks but can retrieve the full parent document for complete context.

This relational link will be managed within a single Qdrant collection, using a doc_type payload field to differentiate between the two types of points.

4.2 Qdrant Payload Schema Definition
The following payload schema is proposed. This schema is optimized for the filtering and retrieval patterns required by the RAG implementation.

Payload Field	Data Type	Indexing	Description & (Source)
doc_type	keyword	Indexed	"parent" or "chunk". The primary filter key.
source_uri	keyword	Indexed	The unique, canonical path to the source file (e.g., "cmos/missions/research/R2.1.md").
parent_id	keyword	Indexed	[For chunks only] The id of the doc_type: "parent" point.
content	text	No Index	[For parents only] The full, raw text of the Markdown document.
chunk_content	text	No Index	[For chunks only] The text of this specific chunk. This is what gets embedded.
front_matter	json	Indexed	The full JSON-parsed YAML front matter. Allows filtering like front_matter.tags: "R2.1".
heading_trail	keyword	Indexed	[For chunks only] An array of headings (e.g., ["Objective", "Context"]).
content_type	keyword	Indexed	[For chunks only] "text", "code_python", "code_js", "table_markdown" (from AST).
chunk_hash	keyword	No Index	md5(chunk_content) for diff-checking and idempotency.
chunk_oversized	bool	Indexed	true if this is an atomic block (code/table) that exceeds the token limit.
last_modified	datetime	Indexed	Filesystem modification timestamp for TTL/staleness checks.
4.3 Integration and Data Flow
Client Connection: The Node.js worker will use the @qdrant/js-client-rest library. Authentication will be handled via an API Key, read from environment variables (QDRANT_API_KEY, QDRANT_URL).

Ingestion Process:

Upon receiving a job (e.g., file_add), the worker parses the file.

It generates one parent point and N chunk points.

A stable UUID (e.g., uuid_v5 from source_uri) is assigned as the parent_id.

Stable UUIDs (e.g., uuid_v5 from parent_id + chunk_hash) are assigned to each chunk point.

Embeddings are generated for the parent.content and all chunk.chunk_content strings.

The worker calls client.upsert with the full list of PointStruct objects.

Idempotency and Deletion:

Idempotency: Because stable, content-derived UUIDs are used, upsert is naturally idempotent. Re-processing a modified file will automatically overwrite the existing parent and chunk points.

Deletion: On a file_delete event, the worker must issue a delete-by-filter command. This command will use the source_uri to remove all points associated with the deleted file in a single, efficient operation.

5. Markdown Ingestion Service: System Blueprint
5.1 Event-Driven Architecture: A Hybrid Watcher-Queue Model
A simple file watcher (like Python's watchdog) coupled directly to the ingestion logic is brittle. A burst of file changes (e.g., a git pull) would overwhelm the service, and a single file-parsing crash (which can be caused by malformed Markdown) could halt all ingestion.

A more resilient, event-driven architecture is required:

Watcher (chokidar): The service will use chokidar, which is the Node.js standard. It normalizes cross-platform file system event inconsistencies that plague the native fs.watch.

Job Dispatch: The only responsibility of the watcher is to detect add, change, and unlink events. It then pushes a simple JSON message (e.g., { "event_type": "upsert", "filepath": "..." }) onto a durable Message Queue.

Job Queue: This queue (e.g., RabbitMQ, SQS) acts as a persistent buffer, ensuring tasks are not lost, providing back-pressure, and enabling retries.

Ingestion Worker(s): A separate, scalable pool of Node.js processes consumes jobs from the queue. This worker contains the unified/remark pipeline and the Qdrant client.

5.2 Benefits of the Decoupled Architecture
This design is inherently modular, scalable, and resilient.

Resilience: If an IngestionWorker crashes while processing a malformed file, the message is un-acknowledged and returned to the queue (or a Dead-Letter Queue). The pipeline does not stop; other workers continue processing.

Scalability: If 10,000 files are added simultaneously, the queue simply fills. The number of IngestionWorker processes can be scaled independently (e.g., via Kubernetes HPA) to drain the queue quickly, without adding load to the single Watcher process.

6. Service Interface Proposal (CLI and API)
6.1 Asynchronous REST API for On-Demand Ingestion
File ingestion is a slow, I/O-bound process involving parsing, network calls to embedding models, and network calls to Qdrant. A synchronous API is guaranteed to time out and is not a resilient pattern. The API must be asynchronous, returning a job ID for polling.

The API's role is not to perform the ingestion but to schedule it. It does this by placing a job on the same Message Queue that the Watcher service uses, unifying all ingestion logic into the Worker pool.

REST API Endpoint Definitions:

7. Risk Assessment and Operational Readiness
7.1 Security Mitigation Plan (OWASP-Aligned)
An ingestion service that parses files from a repository is a primary attack vector. The following mitigations are non-negotiable.

Risk 1: Cross-Site Scripting (XSS)

Threat: The Markdown specification explicitly allows raw HTML. A malicious file containing <script>alert('xss')</script> would be stored in chunk_content. If a downstream UI renders this chunk, the script will execute.

Mitigation: The content must be sanitized. The unified pipeline will be configured with rehype-sanitize. This plugin, which uses the industry-standard DOMPurify, will strip dangerous tags (like <script>) and attributes (like onerror) after parsing but before storage.

Risk 2: Denial-of-Service (DoS) / Parser Exhaustion

Threat: Maliciously crafted Markdown can exploit polynomial-time complexity in parser regular expressions (ReDoS), a vulnerability known as "MarkDownTime". This can cause a single file to consume 100% CPU for minutes, effectively crashing the ingestion worker and halting the entire pipeline.

Mitigation: This is a process-level risk that sanitization cannot fix. The parser must be sandboxed with a non-negotiable timeout. The Node.js IngestionWorker will not run the parser in its main thread. For each file, it will spawn a worker_thread. This sandboxed worker will be given a hard timeout (e.g., 30 seconds). If the unified.process() call does not complete in time, the main thread will terminate the worker. This isolates the DoS attack to a single job, which is logged as a failure, while the main worker process remains healthy and can consume the next job from the queue. This is a far more robust pattern than using Python's signal or multiprocessing workarounds.

Risk 3: Server-Side Request Forgery (SSRF) / File Inclusion

Threat: Markdown extensions for "includes" or embedded assets can be tricked into reading sensitive local files (e.g., --8<-- "/etc/passwd").

Mitigation: The service will run with minimal file system permissions (e.g., in a container). All remark plugins that resolve remote or local assets will be disabled by default. Asset handling must be an explicit, allow-listed feature.

7.2 Performance and Resource Management
Risk: Processing large files (e.g., 500MB - 1GB+) using standard "read file" methods will load the entire file into memory, causing an Out-Of-Memory (OOM) crash.

Mitigation: The IngestionWorker must use streams. The implementation will use fs.createReadStream and pipe it to unified-stream, which processes the document in chunks, ensuring stable and low memory usage regardless of file size.

7.4 Corpus Migration Strategy (Zero-Downtime Backfill)
The existing cmos/missions/research/ corpus must be ingested without interrupting service. (Note: The Qdrant migration tool is for Qdrant-to-Qdrant transfers and is not applicable here).

A phased strategy will be used:

Phase 1: Deploy. The new ingestion service (Watcher, API, Workers) is deployed, but the Watcher service is disabled.

Phase 2: Backfill. The CLI is used to trigger a mass backfill of the existing corpus: ingest run --path "cmos/missions/research/**/*.md". This populates the Qdrant collection. Progress is monitored via the OTel metrics (ingestion.documents.processed) and the API (GET /api/v1/ingest-jobs/...).

Phase 3: Enable Incremental. Once the batch job is completed, the Watcher service is enabled.

This process seeds the semantic cache with the full corpus and seamlessly transitions to incremental updates for any new file changes, achieving the mission goal.
