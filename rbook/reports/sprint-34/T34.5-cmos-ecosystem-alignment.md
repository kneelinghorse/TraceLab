## 2. Sync Health Assessment

From onboarding health check:

| Table | SQLite | PostgreSQL | Delta | Direction |
|-------|--------|------------|-------|-----------|
| sessions | 54 | 50 | +4 | SQLite ahead |
| strategic_decisions | 129 | 100 | +29 | SQLite ahead |
| learnings | 12 | 19 | -7 | PG ahead |

**Root cause**: SQLite is the write-primary store during agent sessions. PG is updated via sync. The deltas indicate:
- **Sessions/decisions (+4/+29)**: Recent sessions haven't been synced to PG. This is expected if sync runs on a cadence, not real-time.
- **Learnings (-7)**: PG has learnings that don't exist locally. Likely created via cmos-dashboard or another agent instance.

**Recommendation**: Add bi-directional sync for learnings. The current uni-directional (SQLite → PG) misses PG-originated records.

## 3. Alignment Opportunities (Ranked by Impact/Effort)

### Opportunity 1: Mission Event Bridge (High Impact / Low Effort)
**What**: TraceLab's mission event bus (`app/core/mission_events.py`) now emits SSE events for mission lifecycle changes. CMOS mission transitions generate similar events but they're trapped in SQLite session_events.

**Alignment**: When `cmos_mission_transition` completes a mission, emit a TraceLab `MissionEvent` to the SSE bus. This lets the Mission Operations Center dashboard show CMOS sprint activity in real-time.

**Implementation**: Add 5-10 lines in the cmos-mcp server's transition handler to POST to TraceLab's event bus or import the emitter directly.

**Effort**: ~1 hour | **Impact**: High — unifies operational visibility

### Opportunity 2: Decision ↔ Insight Linking (Medium Impact / Low Effort)
**What**: CMOS `strategic_decisions` and TraceLab `insights` are conceptually similar — both capture learnings from research work. Currently they exist in separate databases with no cross-references.

**Alignment**: When a CMOS decision references a TraceLab mission (via `mission_id` field), auto-create a TraceLab `Insight` with `insight_type="decision"` and a backlink to the CMOS decision ID.

**Implementation**: Add a post-commit hook in `cmos_decisions` that calls TraceLab's insight API.

**Effort**: ~2 hours | **Impact**: Medium — enriches TraceLab's knowledge graph with operational decisions

### Opportunity 3: Sprint Telemetry Format Standardization (Medium Impact / Low Effort)
**What**: CMOS telemetry events (`cmos/telemetry/events/*.jsonl`) and TraceLab telemetry (`telemetry/events/*.jsonl`) use similar but not identical formats. Both are JSONL with `ts` timestamps but have different field conventions.

**Alignment**: Standardize on a shared event envelope: `{ts, source, event_type, payload}`. Add a `source` field ("cmos" or "tracelab") to distinguish origin. This enables unified dashboards.

**Implementation**: Add `source` field to both emitters. No schema migration needed — JSONL is append-only.

**Effort**: ~30 min | **Impact**: Medium — enables unified telemetry views

### Opportunity 4: Shared Mission ID Namespace (Low Impact / Medium Effort)
**What**: CMOS missions use IDs like "T34.1", "B16.2". TraceLab missions use UUIDs with an optional `mission_id` string field. When a CMOS mission creates a TraceLab mission (e.g., via the tracelab MCP server), the IDs are unrelated.

**Alignment**: When creating TraceLab missions from CMOS context, set TraceLab's `mission_id` to the CMOS mission ID (e.g., "T34.1"). This already partially works — the `context` JSON can store CMOS metadata. Formalize by documenting the convention.

**Implementation**: Documentation + optional validation. No code change required if convention is followed.

**Effort**: ~15 min (docs) | **Impact**: Low — improves traceability but mostly a convention

### Opportunity 5: Dashboard Data Freshness via Cache Invalidation (High Impact / Medium Effort)
**What**: cmos-dashboard may show stale data if it caches CMOS queries. TraceLab's cache manager now has proper per-project invalidation (T34.2). A similar pattern could benefit the dashboard.

**Alignment**: When CMOS data changes (mission transition, decision added), emit a lightweight "data_changed" webhook/event that the dashboard can listen for to trigger SWR revalidation.

**Implementation**: Add webhook emission in cmos-mcp transition handlers. Dashboard subscribes via EventSource or polling.

**Effort**: ~3-4 hours | **Impact**: High — eliminates stale dashboard views

## 4. Anti-Patterns to Avoid

1. **No shared database**: CMOS SQLite and TraceLab PostgreSQL must remain independent. Cross-references should use IDs/URNs, not foreign keys.
2. **No tight coupling**: CMOS tools should work without TraceLab running, and vice versa. All integrations should be fire-and-forget or best-effort.
3. **No schema mirroring**: Don't replicate CMOS tables in PostgreSQL or vice versa. Use API calls for cross-system data access.

## 6. Summary

The CMOS ecosystem is well-structured with clear boundaries. The main alignment gap is **operational visibility** — events from CMOS sprint work don't surface in TraceLab's real-time dashboard, and vice versa. The highest-value, lowest-effort fix is bridging the mission event systems (Opportunity #1), which builds directly on the T34.3 SSE connection fix completed in this sprint.

No hard dependencies should be created. All integrations should follow the pattern: "emit event → best-effort consumer" with graceful degradation if the other system is unavailable.
