Quality Assessment Heuristics for Tiered LLM Routing: A Technical Implementation Guide
A Framework for Heuristic-Based Quality Assessment
This document provides a comprehensive, implementation-ready framework for a quality assessment service designed to enable effective tiered routing in a Large Language Model (LLM) architecture. The primary objective is to furnish a set of actionable, rule-based heuristics to determine when a response from a cost-effective base model (Tier 1: GPT-4o-mini) is of low confidence or quality, thereby requiring escalation to a more capable, higher-cost model (Tier 2: GPT-4o).

Mission Objective and Strategic Context
The strategic imperative for this quality assessment service is rooted in the need to balance performance with operational cost. The project roadmap mandates a tiered LLM strategy where the majority of user queries—over 90%—are handled by the economical Tier 1 model. Escalation to the Tier 2 model is reserved for cases where the base model exhibits clear and detectable signs of failure.

To achieve this, the chosen approach prioritizes deterministic, rule-based heuristics over alternatives such as proprietary LLM confidence score APIs or dedicated machine learning models for quality assessment. This decision is supported by extensive research indicating that model-native confidence scores are often uncalibrated and unreliable; models can exhibit high confidence even when generating factually incorrect or hallucinated content. In contrast, a rule-based system offers high transparency, interpretability, and maintainability, allowing for precise, debuggable logic that aligns with the goal of escalating only on unambiguous failures.   

However, individual rules can be "brittle," failing to generalize across minor variations in language or context. A system that relies on a single heuristic, such as counting specific keywords, would be prone to frequent misclassification, leading to either excessive escalation (violating cost objectives) or insufficient escalation (degrading user experience). To create a robust and reliable system, it is necessary to combine multiple, independent heuristic signals into a composite quality score. This multi-faceted approach mitigates the brittleness of any single rule and provides a more holistic and accurate assessment of response quality.   

The Three Pillars of Quality Assessment
To deconstruct the abstract concept of "low confidence" into measurable components, this framework is built upon three distinct pillars of quality assessment. Each pillar analyzes the LLM's response from a different perspective, and their combined signals provide a robust foundation for the final escalation decision.

Pillar I: Linguistic Uncertainty: This pillar analyzes how the model responds. It focuses on detecting explicit linguistic markers, known as epistemic markers or hedging language, that signal the model's uncertainty about the validity or completeness of its own statements. The presence and type of such language are strong indicators of the model's internal confidence.

Pillar II: Answer Integrity: This pillar analyzes what the model responds. It assesses whether the response is a complete, on-topic, and direct attempt to address the user's query. This includes detecting explicit refusals to answer, identifying when the model responds with a clarifying question instead of an answer, and analyzing whether the response covers the key topics of the user's prompt.

Pillar III: Source Provenance: This pillar analyzes how the model supports its response. In contexts where citations are provided, this pillar validates their quality and authenticity. It focuses on detecting structural flaws such as placeholder text, malformed identifiers, and references to non-existent sources, which serve as strong proxies for hallucination.

By aggregating signals from these three pillars, the quality assessment service can make a more nuanced and reliable determination than would be possible by evaluating any single aspect in isolation.

Architectural Role and Integration
The quality assessment service is designed to function as a synchronous, post-processing middleware component within the tiered routing architecture. It intercepts every response generated by the Tier 1 model before it is returned to the end-user, executing a series of heuristic checks to compute a final quality score.

The data flow follows the "Confidence-based LLM Cascade" pattern :   

A user's prompt is initially sent to the Tier 1 LLM (GPT-4o-mini).

The Tier 1 LLM generates a response.

This response, along with the original prompt, is passed to the Quality Assessment Service.

The service executes the heuristics defined in this document to calculate a composite Quality Score.

The Quality Score is compared against a predefined Escalation Threshold.

If the score is below the threshold, the service signals for escalation. The original prompt is then re-routed to the Tier 2 LLM (GPT-4o), and its response is returned to the user.

If the score is at or above the threshold, the Tier 1 response is deemed acceptable and is returned directly to the user.

This architecture ensures that the more expensive Tier 2 model is invoked only when there is a quantifiable, evidence-based reason to believe the Tier 1 model has failed, thereby adhering to the project's core cost-optimization and quality assurance objectives.

Pillar I: Linguistic Uncertainty and Hedging Detection
The first pillar of quality assessment focuses on analyzing the linguistic characteristics of the model's output to detect expressions of uncertainty. LLMs, when uncertain, often employ hedging language or "epistemic markers" in a manner that mimics human communication. While research indicates that an LLM's use of this language may not be perfectly calibrated to its internal confidence state , the presence of such markers remains a valuable and detectable signal of potential low confidence. An LLM may lack natural hedging unless explicitly prompted, but when it does appear, it warrants scrutiny.   

The Psychology of Hedging and Epistemic Markers
In human communication, hedging serves to express a lack of full commitment to the truth of a statement. This can be due to a genuine lack of knowledge (internal uncertainty) or because the topic itself is inherently probabilistic or ambiguous (external uncertainty). For the purpose of tiered routing, detecting signals of internal uncertainty is paramount. When a model uses phrases like "I am not sure" or "I believe," it is explicitly signaling a limitation in its own knowledge or reasoning capabilities. This is a direct indication that a more powerful model might be required to provide a more definitive answer.   

Conversely, expressions of external uncertainty or simple approximators (e.g., "The population is approximately 10 million") are weaker signals. They may simply reflect the nature of the information being conveyed rather than a failure of the model. Therefore, the detection mechanism must be nuanced, capable of distinguishing between different categories of hedging and weighting them accordingly.

A Categorized Catalog of Hedging Language
To enable a weighted scoring system, hedging patterns are classified into four categories based on their likely impact and the type of uncertainty they convey.

Category 1: Shields (High-Impact): These patterns indicate a direct lack of commitment to the proposition's truth and are strong signals of low confidence. They often involve first-person epistemic phrases that explicitly reference the speaker's (the model's) internal state.

Introductory Verbs: seem, tend, appear to be, think, believe, assume, suggest, indicate.   

First-Person Epistemic Phrases: I think, I believe, I assume, I am not sure, In my opinion, it is my understanding.   

Category 2: Modal Verbs (Medium-Impact): These verbs express possibility, probability, or weak obligation rather than certainty. Their presence reduces the definitiveness of a statement.

List: may, might, could, should, would.   

Category 3: Approximators (Low-Impact): These patterns indicate a lack of precision, which is not necessarily the same as a lack of confidence in the core assertion. They are weaker signals for escalation.

Adverbs: roughly, approximately, largely, usually, often, sometimes, perhaps, possibly, probably, conceivably, apparently.   

Adjectives: possible, probable, likely, unlikely.   

Vague Language: about, kind of, sort of, seems like.   

Category 4: Grammatical Patterns: These are introductory phrases that frame the entire statement as uncertain or debatable.

Introductory Phrases: it appears that, it can be argued that, it is possible that, it seems that, there is a possibility that.

def detect_hedging(text: str) -> dict:
    """
    Detects and counts hedging language patterns in a given text.

    Args:
        text: The LLM response string to analyze.

    Returns:
        A dictionary with counts for each category of hedging.
    """
    counts = {
        "shields": 0,
        "modals": 0,
        "approximators": 0,
        "grammatical": 0
    }

    for category, pattern in HEDGING_PATTERNS.items():
        matches = pattern.findall(text)
        counts[category] = len(matches)

    return counts

Pillar II: Answer Integrity and Completeness
The second pillar of quality assessment evaluates the fundamental integrity of the response. A linguistically confident and well-cited answer is of no value if it fails to address the user's query, is incomplete, or is an outright refusal to engage. This section defines three key heuristics to ensure the response is a direct, substantive, and complete attempt to fulfill the user's request. These heuristics are designed to work in concert; an explicit refusal is a clear failure, while a low content coverage score can detect more subtle "soft refusals" where the model provides a generic, unhelpful answer without explicitly declining the prompt.

Detecting Unanswered and Partially Answered Questions
A common failure mode for an LLM that lacks the necessary information or capability to answer a query is to respond with a clarifying question. For example, if asked to "Summarize the report," a model that cannot access the report might reply, "Could you please provide the text of the report you would like me to summarize?" This indicates an inability to proceed and is a strong signal that the query should be escalated to a more capable model that may have the required context or functionality.

Algorithm: Question Detection in Response
A rule-based algorithm can reliably detect the presence of questions within the LLM's generated text.

Sentence Segmentation: The response text is first segmented into individual sentences.

Rule-Based Question Identification: Each sentence is evaluated against a set of linguistic and structural rules. A sentence is classified as a question if it meets any of the following criteria:

Punctuation: The sentence ends with a question mark (?). This is the most direct signal.

Interrogative Keywords: The sentence begins with a common interrogative word (a "wh-word") such as what, which, who, whom, when, where, why, or how.   

Inverted Syntax: The sentence begins with an auxiliary verb before the subject, a common structure for yes/no questions (e.g., is, are, was, were, do, does, did, can, could, will, would).   

Syntactic Parsing (Advanced): For higher accuracy, a syntactic parser can be used to analyze the grammatical structure of the sentence. The presence of Penn Treebank tags such as SBARQ (direct question) or SQ (inverted yes/no question) provides a very reliable indicator that the sentence is interrogative.   

If one or more sentences in the response are classified as questions, the entire response is flagged as incomplete, signaling a need for escalation.

Content Coverage Analysis (Simplified)
For multi-faceted or complex prompts, it is crucial to verify that the LLM's response addresses all key aspects of the query. An answer that only addresses one part of a two-part question is incomplete. This heuristic provides a simplified, non-LLM-based method for estimating content coverage, inspired by evaluation metrics used in text summarization and RAG systems.   

Algorithm: Keyword-Based Content Coverage
Key Term Extraction from Prompt: The original user prompt is processed to extract a set of essential keywords and named entities. This can be achieved using standard Natural Language Processing (NLP) techniques such as part-of-speech (POS) tagging to identify nouns and proper nouns, followed by noun phrase chunking. For example, in the prompt "Compare the legislative and judicial branches of the US government," the key terms would be legislative branch, judicial branch, and US government. A stop-word list should be applied to filter out common, non-substantive words.   

Term Presence Check in Response: The system then iterates through the extracted key terms and checks for their presence in the LLM's response. To account for linguistic variation, this check should be case-insensitive and can be enhanced with a simple, predefined thesaurus to match synonyms (e.g., legislative could match Congress).

Coverage Score Calculation: A quantitative coverage score is computed as the proportion of key terms from the prompt that were successfully found in the response.

Detecting Explicit Refusals
The most direct signal of a model's inability or unwillingness to answer a prompt is an explicit refusal. Safety-aligned models are trained to decline requests that are harmful, unethical, or fall outside their designated capabilities. Detecting these refusal patterns is a critical, high-precision heuristic for triggering escalation, as it signifies that the base model has already made a definitive judgment that it cannot fulfill the request.   

Pattern Library for Refusal Detection
A comprehensive library of common refusal phrases and patterns is essential for this heuristic. These patterns can be detected using case-insensitive regular expression matching.

Direct Refusals: Phrases that state inability directly.

Examples: "I cannot," "I can't," "I am unable to," "I will not," "I'm not able to."

Regex: \b(I(?:\'m|\s+am)\s+(not\s+able|unable)\s+to|I\s+(cannot|can\'t|will\s+not))\b.   

Apologetic Refusals: Refusals preceded by an apology.

Examples: "I'm sorry, but I cannot," "I apologize, but I am unable to."

Regex: \b(I\'?m\s+sorry|I\s+apologize),\s+but\b.   

Capability Disclaimers: Phrases that deflect based on the model's identity as an AI.

Examples: "As an AI model," "As a large language model," "I do not have the ability to."

Regex: \b(as\s+an\s+(AI|large\s+language\s+model)|I\s+do\s+not\s+have\s+the\s+ability\s+to)\b.   

Ethical and Safety Disclaimers: Refusals based on safety guidelines or ethical principles.

Examples: "That request goes against my safety guidelines," "It would be inappropriate to," "I cannot create content of that nature."

Regex: \b(goes\s+against\s+my\s+safety|inappropriate\s+to|content\s+of\s+that\s+nature)\b.   

Any match for these patterns should be treated as a high-severity failure, immediately flagging the response for escalation.

Pillar III: Source Provenance and Citation Validation
The third pillar of quality assessment addresses the reliability of information by validating the sources cited in the LLM's response. LLMs are known to "hallucinate," frequently generating citations that appear plausible but are factually incorrect, malformed, or entirely fabricated. This is a critical failure mode, as a response supported by fake sources is fundamentally untrustworthy.   

The goal of this pillar is not to perform a deep semantic analysis of whether a source supports a claim—a task that often requires another LLM and is outside the scope of this rule-based framework. Instead, the focus is on performing a series of low-cost, deterministic, structural checks to detect common and obvious signs of citation failure. The presence of such flaws serves as a strong proxy indicator that the overall response quality is low and likely contains hallucinated content.   

Taxonomy of Common Citation Failures
LLM-generated citations are prone to several distinct types of errors that can be detected with rule-based methods.

Fabricated or Fictional Citations: The model invents a source that does not exist. This can include creating fake article titles, author names, or journal volumes. While difficult to detect without external verification, they often co-occur with other structural flaws.   

Placeholder Text: The model explicitly indicates a missing citation with placeholder text. This is a definitive sign of failure and one of the easiest to detect. Examples include [citation needed], [source], or empty brackets ``.   

Malformed Citations: The citation is structurally incorrect. This includes malformed identifiers (e.g., an invalid DOI or ISBN format) or missing critical components (e.g., an author-date citation with no date).   

Incorrect References: The citation refers to a real source, but it is incorrect in the context of the answer. For example, the reference does not support the specific proposition it is cited for. This is a semantic error and is generally out of scope for this heuristic framework, but can sometimes be caught if it involves identifier mismatches.

Implementation Workflow
Citation Extraction: First, use regular expressions to identify and extract all potential citations from the response text. Patterns to look for include bracketed numbers (e.g., \[[0-9]+\]), parenthetical author-date formats (e.g., \([A-Za-z\s]+,\s*\d{4}\)), and inline identifiers like DOIs and ISBNs.

Placeholder Detection (High-Severity Check): Scan the entire response for any of the placeholder patterns defined in Table 2. The presence of even a single placeholder like [citation needed] is an unambiguous signal that the model failed to find or insert a proper source and should trigger an immediate high-severity failure flag for this pillar.

Identifier Formatting and Validation: For each extracted citation:

Attempt to identify and extract any standard identifiers (DOIs, ISBNs).

If an identifier is found, validate its format against the corresponding regex from Table 2. A format mismatch is a medium-severity failure.

A checksum validation for ISBNs is computationally more complex and can be omitted in the initial implementation, as regex-based format checking provides a strong first-pass filter.   

Lightweight External Verification (Optional):

For any citation containing a structurally valid DOI, execute a non-blocking, time-limited API call to a public resolver like doi.org.   

Workflow:

Send an HTTP HEAD or GET request to https://doi.org/api/handles/{doi}.

If the server responds with an HTTP 404 Not Found status, the DOI is non-existent. This is a high-severity failure.

If the server responds with an HTTP 200 OK or a redirect (3xx), the DOI is valid.

To prevent latency, this check must have a strict timeout (e.g., 500 milliseconds). If the request times out or fails for network reasons, it should be treated as a neutral result (pass), not a failure.

Structural Integrity Check: For citations without standard identifiers, perform basic structural checks. For an author-date style, this could be as simple as verifying the presence of text that looks like a name and a plausible year. This is a low-severity check designed to catch grossly malformed entries.

The output of this pillar should be a count of invalid citations, categorized by the severity of the failure. This allows for a nuanced contribution to the final quality score, where a non-existent DOI penalizes the score more heavily than a simple formatting error.

Integrated Quality Scoring and Escalation Logic
The final step in the quality assessment process is to synthesize the discrete signals from the three pillars—Linguistic Uncertainty, Answer Integrity, and Source Provenance—into a single, actionable quality score. This score is then used in a structured decision process to determine whether to escalate the query to the Tier 2 model. The goal is to create a system that is both sensitive to clear, high-severity failures and capable of identifying responses that are degraded by a combination of smaller issues.

Rationale: This value is selected as a balanced starting point based on common industry practices for quality metrics, where scores below 85-90% often indicate a need for review. The threshold is intentionally set to be reasonably strict to ensure that clear failures are caught. However, this is an empirical value that must be tuned.   

Tuning Strategy:

Shadow Mode Deployment: Initially, the quality assessment service should be deployed in a "shadow mode." It will process all Tier 1 responses and calculate a Q_score without actually triggering escalation.

Data Collection: Log the Q_score distribution for a large volume of production traffic (e.g., 100,000+ requests).

Threshold Calibration: Analyze the score distribution to determine the threshold value that corresponds to the 10th percentile. Setting the Escalation_Threshold to this value will empirically achieve the target 10% escalation rate. For example, if 10% of responses have a Q_score below 0.78, then 0.78 becomes the new threshold.

Iterative Refinement: The weights and threshold should be periodically re-evaluated as model behaviors and user query patterns evolve.

FUNCTION calculate_coverage_score(prompt_text, response_text):
  // 1. Extract key terms from the prompt
  prompt_tokens = tokenize(prompt_text)
  prompt_pos_tags = part_of_speech_tag(prompt_tokens)
  key_terms = extract_noun_phrases_and_proper_nouns(prompt_pos_tags)
  filtered_key_terms = remove_stopwords(key_terms)

  IF count(filtered_key_terms) == 0:
    RETURN 1.0 // No key terms to check, default to pass

  // 2. Check for presence in the response
  found_terms_count = 0
  response_lower = to_lowercase(response_text)

  FOR each term in filtered_key_terms:
    term_lower = to_lowercase(term)
    IF term_lower is in response_lower:
      found_terms_count += 1

  // 3. Calculate score
  coverage_score = found_terms_count / count(filtered_key_terms)
  RETURN coverage_score

CITATION_FAILURE_WEIGHTS = {"high": 1.0, "medium": 0.5, "low": 0.2}
PILLAR_WEIGHTS = {"lu": 0.3, "ai": 0.5, "sp": 0.2}

class QualityAssessor:
    def __init__(self):
        # Compile regex patterns for efficiency
        self.refusal_pattern = re.compile(r'\b(I(?:\'m|\s+am)\s+(not\s+able|unable)\s+to|I\s+(cannot|can\'t|will\s+not)|I\'?m\s+sorry,\s+but|as\s+an\s+(AI|large\s+language\s+model)|inappropriate\s+to|against\s+my\s+safety)\b', re.IGNORECASE)
        self.placeholder_citation_pattern = re.compile(r'\[\s*(citation\s+needed|source|placeholder|ref)\s*\]|\[\s*\]', re.IGNORECASE)
        self.question_pattern = re.compile(r'^(what|which|who|when|where|why|how|is|are|do|does|can|could)\b.*\?$|.*\?$', re.IGNORECASE)
        # Add other patterns...

    # --- Pillar I: Linguistic Uncertainty ---
    def _calculate_lu_score(self, text: str) -> float:
        # Implementation of detect_hedging from Section 2
        #... returns counts dict
        # For demonstration:
        counts = {"shields": 1, "modals": 2, "approximators": 3, "grammatical": 0} # Dummy data
        word_count = len(text.split())
        if word_count == 0: return 1.0

        penalty = (HEDGING_WEIGHTS["shields"] * counts["shields"] +
                   HEDGING_WEIGHTS["modals"] * counts["modals"] +
                   HEDGING_WEIGHTS["approximators"] * counts["approximators"] +
                   HEDGING_WEIGHTS["grammatical"] * counts["grammatical"]) / word_count
        
        return max(0.0, 1.0 - penalty)

    # --- Pillar II: Answer Integrity ---
    def _detect_refusal(self, text: str) -> bool:
        return bool(self.refusal_pattern.search(text))

    def _detect_question_in_response(self, text: str) -> bool:
        sentences = text.split('.') # Simplified sentence splitting
        for sentence in sentences:
            if self.question_pattern.search(sentence.strip()):
                return True
        return False

    def _calculate_coverage_score(self, prompt: str, response: str) -> float:
        # Simplified implementation of pseudo-code
        prompt_keywords = set(prompt.lower().split()) - {"the", "a", "an", "is", "what", "how"}
        if not prompt_keywords: return 1.0
        response_lower = response.lower()
        found_count = sum(1 for keyword in prompt_keywords if keyword in response_lower)
        return found_count / len(prompt_keywords)

    def _calculate_ai_score(self, prompt: str, response: str) -> float:
        s_refusal = 0.0 if self._detect_refusal(response) else 1.0
        s_question = 0.0 if self._detect_question_in_response(response) else 1.0
        s_coverage = self._calculate_coverage_score(prompt, response)
        return s_refusal * s_question * s_coverage

    # --- Pillar III: Source Provenance ---
    def _calculate_sp_score(self, text: str) -> float:
        # Simplified implementation of citation validation
        if self.placeholder_citation_pattern.search(text):
            return 0.0 # Hard failure for placeholders
        # Add logic for DOI/ISBN format checks and external validation
        # For now, we assume no other errors if no placeholders are found.
        return 1.0

    # --- Main Assessment Logic ---
    def assess_quality(self, prompt: str, response: str) -> Tuple:
        """
        Assesses the quality of an LLM response and determines if escalation is needed.

        Returns:
            A tuple of (should_escalate, quality_score, detailed_scores).
        """
        # 1. Check for hard failures (from Decision Tree)
        if self._detect_refusal(response):
            return True, 0.0, {"ai_score": 0.0, "reason": "Explicit Refusal"}
        if self.placeholder_citation_pattern.search(response):
            return True, 0.0, {"sp_score": 0.0, "reason": "Placeholder Citation"}
        if self._detect_question_in_response(response):
            return True, 0.2, {"ai_score": 0.0, "reason": "Question in Response"} # Score > 0 but still escalates

        # 2. Calculate composite score
        score_lu = self._calculate_lu_score(response)
        score_ai = self._calculate_ai_score(prompt, response)
        score_sp = self._calculate_sp_score(response)

        detailed_scores = {"lu_score": score_lu, "ai_score": score_ai, "sp_score": score_sp}

        q_score = (PILLAR_WEIGHTS["lu"] * score_lu +
                   PILLAR_WEIGHTS["ai"] * score_ai +
                   PILLAR_WEIGHTS["sp"] * score_sp)

        # 3. Threshold-based decision
        should_escalate = q_score < ESCALATION_THRESHOLD

        return should_escalate, q_score, detailed_scores

The framework is built on three pillars—Linguistic Uncertainty, Answer Integrity, and Source Provenance—each targeting a distinct and measurable dimension of response quality. The synthesis of these signals into a unified, weighted quality score, combined with a hybrid decision tree that prioritizes high-severity failures, creates a system that is more robust and nuanced than any single heuristic could be in isolation.
