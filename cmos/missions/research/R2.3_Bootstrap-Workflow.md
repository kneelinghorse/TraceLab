Project Bootstrap Workflow: R2.3 Architectural Design Specification
This document provides the complete architectural design specification for the Project Bootstrap Workflow, as defined in Mission File R2.2. The objective is to deliver a scriptable, production-grade workflow for project and document onboarding, replacing the current manual SQL-based processes.

> Decision (2025-11-05): Current deployment operates in trusted single-user mode with no authentication or CLI requirement. Device-authorization and Typer CLI guidance below is retained for future multi-user expansion.

This system is a critical dependency for unblocking testing in Sprint B2.3. The architecture is designed to be resilient, observable, and extensible for future UI-driven workflows. It is centered on four key architectural pillars:

A Command-Line Interface (CLI): A new ingest-cli will provide an ergonomic, scriptable interface for agents, abstracting all underlying database interactions.

An Asynchronous API: A RESTful Onboarding API will serve as the backend for the CLI. It will manage metadata and, critically, handle long-running ingestion tasks using an asynchronous HTTP 202 Accepted pattern, which decouples the client from the work.

A Resilient Data Consistency Model: The multi-step ingestion process (SQL write, message queue, Markdown parsing, embedding, Qdrant write) is a distributed transaction. This system will manage data consistency using the Saga Pattern with Compensating Transactions to handle partial failures and ensure a predictable state.

End-to-End Observability: The entire workflow, from the initial CLI command to the final vector database write, will be tracked using OpenTelemetry distributed tracing. This provides essential debugging capabilities for a complex, distributed, and asynchronous system.

Part 1: The ingest-cli Command-Line Interface Specification
The ingest-cli is the primary tool agents will use to interact with the ingestion system. The design philosophy emphasizes ergonomics, discoverability, and human-readable feedback , while adhering to established CLI conventions.   

1.1. Technology Recommendation: Python + Typer
The CLI will be implemented in Python using the Typer framework.   

This choice is driven by ecosystem cohesion. The recommended backend API (see Part 2) is FastAPI. Typer is built by the same author and shares the identical design paradigm: Python type hints are used directly for validation and serialization. This reduces the cognitive load for developers working across the stack.   

Furthermore, Typer provides straightforward patterns for creating nested subcommands , which directly supports the noun verb command structure, and has clear recipes for integrating YAML-based configuration files , a technology explicitly under investigation.   

1.2. Configuration and Environment Management
The CLI must manage configuration securely and flexibly, supporting multiple environments (e.g., local, staging, production) without hardcoded values.   

Environment Variables: All configuration parameters can be supplied via environment variables (e.g., INGEST_API_URL, INGEST_AUTH_CLIENT_ID). This adheres to the 12-Factor App methodology and is the preferred method for CI/CD environments.   

Configuration File: For agent convenience, the CLI will also read configuration from a YAML file located at a standard XDG config path (e.g., ~/.config/ingest/config.yml).   

Precedence: Configuration will be loaded in the following priority: (1) Environment Variables, (2) Configuration File values, (3) Hardcoded defaults.

Contexts: The YAML configuration file will support a "contexts" model, allowing agents to define and switch between different target environments easily.

Example config.yml:

YAML
# The context to use if --context flag is not provided
current_context: "local"

contexts:
  local:
    api_url: "http://localhost:8000"
    auth_client_id: "cli_client_local"
  staging:
    api_url: "https://api.staging.our-domain.com"
    auth_client_id: "cli_client_staging"
1.3. Authentication: ingest-cli auth login
The CLI is a public, "headless" client. It operates on limited-input devices (a terminal) and cannot securely store a client secret, making it incompatible with the standard OAuth 2.0 Authorization Code flow.   

Therefore, the CLI must implement the OAuth 2.0 Device Authorization Flow.   

The ingest-cli auth login command will orchestrate this flow:

The CLI makes an unsupervised POST request to the authorization server's device endpoint (e.g., https://auth.our-domain.com/login/device/code).   

The auth server responds with a user_code (e.g., ABC-123), a verification_uri (e.g., https://auth.our-domain.com/login/device), and a device_code.   

The CLI prints a human-readable message: Please visit: https://auth.our-domain.com/login/device And enter code: ABC-123

Simultaneously, the CLI begins polling the auth server's token endpoint in the background, sending the device_code.

The agent authenticates in their browser using the user_code.

The next poll request succeeds, and the CLI receives an access_token and a refresh_token.   

These tokens are stored securely in the local filesystem (e.g., ~/.config/ingest/creds.json) with strict permissions. The refresh_token will be used to silently acquire new access_tokens when they expire, ensuring a smooth agent experience.

1.5. User Feedback and Error Handling
Errors are a primary blocker for developers. The CLI must translate cryptic backend errors into human-readable, actionable feedback.   

Success Feedback: Every successful action must provide clear, affirmative feedback.   

Bash
$ ingest-cli project create "Sprint 02 Testing"
✔ Success: Project 'Sprint 02 Testing' (id: proj_abc123) created.
Progress Feedback: For long-running commands (i.e., --wait), the CLI must display visual progress (e.g., a spinner) to indicate the system is working, not hung.   

Bash
$ ingest-cli document register./docs/intro.md --project proj_abc123 --ingest --wait
⠧ Registering document...
✔ Success: Document 'intro.md' (id: doc_xyz789) registered. Job ID: job_123
⠇ Ingesting (job_123): PENDING...
⠇ Ingesting (job_123): PARSING...
⠇ Ingesting (job_123): EMBEDDING...

Human-Readable Errors: The CLI must catch API error responses and re-format them. It should describe what went wrong, the reason, and a potential next step.

Part 2: The Onboarding API Contract (REST)
This new Onboarding API provides the single service boundary abstracting the project and document metadata database. It is a RESTful API, designed for platform independence and loose coupling, ensuring that future UIs or services can consume it.   

2.1. Resource Modeling
The API will be designed around three core resources:

Project: The top-level container for organizing documents. It holds project-level configuration and metadata.

Document: A record representing a single piece of content (e.g., a Markdown file) that belongs to a Project. This resource contains metadata and, critically, a status field (PENDING, INGESTING, COMPLETED, FAILED). This status field serves as the state machine for the ingestion Saga.

IngestionJob: A resource representing a single run of the ingestion pipeline. This resource is the target for status polling.   

2.2. Authentication: OAuth 2.0 + OIDC
The API will be secured as an OAuth 2.0 Resource Server.

All requests must include an Authorization: Bearer <access_token> header.

The API will validate the incoming JWT (the access token) against the authorization server's public keys.

The API will use OpenID Connect (OIDC) claims within the token, specifically the sub (subject) claim, to identify the user and enforce authorization policies (e.g., "User A can only list projects they own").   

2.3. Cross-Cutting Concern: Idempotency
Network environments are inherently unreliable. A client (like the CLI) that experiences a timeout on a POST request cannot know if the operation succeeded. If the client retries a non-idempotent POST, it will create duplicate resources.   

To prevent this data corruption, all state-changing endpoints (POST, PUT, PATCH) must be idempotent.   

Specification: These endpoints must support the Idempotency-Key: <UUID> request header.   

Server-Side Logic:

The CLI generates a unique UUID for the Idempotency-Key header before sending the request.

The server receives the request (e.g., POST /projects) and checks a high-speed cache (e.g., Redis) for this key.

If Key is Found: The server immediately returns the cached response (e.g., the original 201 Created response) without re-executing the business logic.

If Key is Not Found: The server executes the business logic (e.g., creates the project in the DB), stores the resulting response (e.g., 201 Created + project object) in the cache against the key, and then returns that response to the client.

This pattern ensures that client-side retries are safe and do not create duplicate data.   

2.4. Cross-Cutting Concern: Asynchronous Ingestion Pattern
Document ingestion (parsing, embedding, vector storage) is a long-running task that will exceed standard HTTP timeout thresholds. Therefore, ingestion-triggering endpoints cannot be synchronous.   

Specification: All endpoints that trigger ingestion must implement the Asynchronous Request-Reply Pattern.   

Workflow Sequence:

Client Request: The CLI sends POST /documents/{documentId}/ingest.

Server Acceptance: The API synchronously validates the request, creates an IngestionJob resource with status: "PENDING", and enqueues the job in a message broker (e.g., Celery/RabbitMQ).   

Server Response: The API immediately returns an HTTP 202 Accepted status code. This response must include a Location header pointing to the IngestionJob status endpoint.   

HTTP/1.1 202 Accepted

Location: /jobs/job_12345

Body: {"jobId": "job_12345"}

Client Polling: The CLI (if in --wait mode) receives the 202 response, extracts the Location header, and begins polling the GET /jobs/job_12345 endpoint.

Status Check: The polling endpoint (GET /jobs/{jobId}) returns an HTTP 200 OK with the current status of the job. The CLI continues polling until the status is COMPLETED or FAILED.   

JSON
{
  "jobId": "job_12345",
  "status": "INGESTING", // PENDING, INGESTING, COMPLETED, FAILED
  "steps":,
  "error": null
}
This design decouples the client from the long-running process, ensuring the API remains responsive and scalable.

Part 3: End-to-End Workflow and Service Interaction
This section details the interaction between the components, forming an event-driven architecture to decouple the synchronous API from the asynchronous Markdown Ingestion Service.   

3.1. Component Architecture
ingest-cli: (Agent's Machine) The user-facing client. Makes synchronous HTTP calls to the Onboarding API.

Onboarding API: (e.g., FastAPI) The synchronous service boundary. Manages metadata in the SQL Database. It is a publisher of ingestion tasks.

SQL Database: (e.g., PostgreSQL) The source of truth for all project and document metadata, including ingestion status.

Message Broker: (e.g., RabbitMQ, Kafka) The asynchronous communication backbone. Decouples the API from the ingestion service.   

Markdown Ingestion Service: (e.g., Celery Worker) An asynchronous, scalable service that is a consumer of ingestion tasks. It performs the heavy lifting.   

Embedding Service: (e.g., OpenAI API) An external service called by the Ingestion Service to generate vectors.

Qdrant: The vector database where the final embeddings and payloads are stored.

Part 4: Resilience, Observability, and Risk Management
This section fulfills the requirements for failure recovery and observability. In a distributed system, failure is a normal operating condition. The architecture must be designed to handle it gracefully.

4.1. Observability: End-to-End Distributed Tracing
To debug a failed ingestion, it is necessary to view the entire request lifecycle as a single, unified trace. Siloed logs are insufficient.   

Specification (OpenTelemetry):

ingest-cli: The CLI will be instrumented with the OpenTelemetry Python SDK. Before any API call, it will start a root span and inject the W3C traceparent header into the HTTP request.   

Onboarding API: The FastAPI application will use automatic instrumentation (e.g., opentelemetry-instrumentation-fastapi). This will automatically read the incoming traceparent header and create a child span for the API request.   

Message Propagation: When the API publishes the job to the message broker, it must inject the active traceparent context into the message payload (as shown in section 3.3).

Ingestion Svc: The Celery worker will use opentelemetry-instrumentation-celery. This will automatically extract the traceparent context from the message and create subsequent spans for each step: parsing, calling the embedding API (via opentelemetry-instrumentation-httpx) , and writing to Qdrant.   

Result: A single traceId will correlate the agent's command, the API request, the time spent in the queue, every step of the ingestion service, the call to the external embedding API, and the final vector database write. This provides complete end-to-end visibility for debugging.

4.2. Resilience: The Saga and Compensating Transactions
The ingestion workflow is a Saga: a sequence of local transactions (DB write, file parse, embedding call, Qdrant write). If any step after the first one fails, the system is left in an inconsistent state. The Compensating Transaction Pattern is required to undo prior work or formally mark the operation as failed.   

Strategy: The Markdown Ingestion Service is the orchestrator of the core ingestion saga. The status field on the Document resource in the SQL DB is the central state machine.

Failure Scenario Walkthrough: Qdrant Write Fails

Action: The IngestionSvc successfully parses the document and receives vectors from the Embedding Service.

Failure: It attempts qdrant_client.upsert(...). Qdrant returns an HTTP 400 Bad Request with the error: Vector dimension error: expected dim: 1536, got 512.   

Failure Handling (Saga): The service's except block catches this non-transient exception.

Compensating Transaction: The service must execute a compensating transaction. It writes the failure state back to the source of truth (the SQL DB):

UPDATE documents SET status = 'FAILED', error_message = 'Qdrant dimension mismatch: 1536 vs 512' WHERE id = 'doc_xyz789'

UPDATE jobs SET status = 'FAILED', error_message = '...' WHERE id = 'job_12345'

Result (System Consistency): The system is now consistent. The agent's polling GET /jobs/job_12345 request returns the FAILED status with the actionable error message. The document is not queryable, and the failure is clearly recorded.

4.3. Resilience: Idempotent Vector Writes
Message brokers (like RabbitMQ) often provide "at-least-once" delivery, meaning a worker could, in rare cases, receive the same ingestion job message twice. This would lead to duplicate vectors in Qdrant, corrupting search results.   

Specification: All Qdrant writes must be idempotent.

Implementation: Qdrant's upsert operation is idempotent if the point id is stable. The IngestionSvc must generate a deterministic UUID (e.g., UUIDv5) for every vector "point" it creates, based on the document ID and the chunk index.   

point_id = uuid.v5(namespace=document_id, name=f"chunk_{chunk_index}")

Result: If a message is processed twice, the second upsert operation will simply overwrite the existing points with the exact same IDs, vectors, and payloads. This prevents data duplication and makes the pipeline robust against message redelivery.

Part 5: Validation Strategy and Developer Bootstrap
This section provides the actionable plans for agents to configure their environments and for the team to test the system end-to-end.

5.1. Environment Bootstrap Checklist
This checklist provides the steps for an agent or developer to set up a local, fully-functional development environment.   

[ ] Clone the ingest-cli and onboarding-api repositories.

[ ] Install Python 3.10+ (or as specified in the projects).

[ ] Run make install (or equivalent) in both repositories to create virtual environments and install all dependencies.   

[ ] Install and run local service dependencies via Docker Compose:

[ ] docker compose up -d postgres qdrant rabbitmq

[ ] Run database migrations for the Onboarding API to initialize the schema.

[ ] Create a local ~/.config/ingest/config.yml file, pointing the local context api_url to http://localhost:8000 (see section 1.2).

[ ] (First time only) Run a local seed script to configure the (mocked) Auth Server with the cli_client_local client ID.

[ ] Run the API locally: uvicorn app.main:app --reload

[ ] Run the Ingestion Service locally: celery -A app.worker worker --loglevel=info

[ ] Verify the complete setup by running ingest-cli auth login and confirming authentication, followed by ingest-cli project list.

Conclusion
This architectural specification defines a complete, resilient, and observable workflow for project and document onboarding. By implementing the ingest-cli and the asynchronous Onboarding API, all manual SQL dependencies for agent-based testing are removed, fulfilling the primary objective of Mission File R2.2.

The core patterns—OAuth 2.0 Device Flow for auth, Asynchronous Request-Reply for ingestion, Idempotency for retries, and the Saga pattern for failure management—provide a robust foundation. The integration of end-to-end OpenTelemetry tracing ensures the system is debuggable and maintainable. This design unblocks immediate testing needs for B2.3 and provides a scalable, extensible platform for future ingestion and application development.
