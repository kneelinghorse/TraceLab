Executive Summary: Diagnostic Findings and Corrective Actions
Diagnostic Finding (Root Cause): The persistent "Collection 'research_chunks' doesn't exist" error, culminating in a 404 Not Found during upsert_chunks(), is a symptom of a critical, underlying connection and authentication failure. The investigation confirms the root cause is a fundamental mismatch between the application's QdrantClient initialization logic and the Qdrant server's configuration. This mismatch exists and manifests identically in both the local (localhost:6333) and hosted (qdrant-production-1e32.up.railway.app) environments.

The "Smoking Gun": The key diagnostic datum is the log warning: "Api key is used with unsecure connection". This UserWarning from the qdrant-client library provides two irrefutable facts about the application's current state:   

The QdrantClient is being initialized with a non-null api_key parameter.

The QdrantClient is attempting to connect to a URL that uses http:// (an unencrypted channel), not https://.

The Two-Environment Paradox Explained: The identical failure in both environments stems from this single misconfiguration.

Hosted (Railway): The application is connecting via http:// and sending an api_key. The Railway-hosted Qdrant instance, deployed from a default Docker image , does not have authentication enabled by default. The server, therefore, is not configured to receive an API key and rejects the authenticated request.   

Local (Docker): The exact same failure occurs. The client connects to http://localhost:6333 and sends an api_key. The default local Qdrant server also has no authentication enabled. This server also rejects the unexpected authenticated request.   

The ensure_collection() function is not "failing silently"; rather, the QdrantClient it instantiates is failing to connect at all, and this initial connection exception is likely being improperly handled or suppressed by the application.

Corrective Actions:

Enable Server-Side Auth (Railway): The Qdrant service on Railway must be configured with the environment variable QDRANT__SERVICE__API_KEY=your_secret_key. This action, documented in Qdrant's security guide , instructs the server to require this API key.   

Correct Client-Side Config (Application): The application must be configured using two environment variables: QDRANT_URL and QDRANT_API_KEY.

For Railway, QDRANT_URL must be https://qdrant-production-1e32.up.railway.app and QDRANT_API_KEY must match the key from step 1.   

For Local, QDRANT_URL must be http://localhost:6333 and QDRANT_API_KEY must be unset (or None).

Recommended Lifecycle Strategy: The collection must be created idempotently on application startup. This "fail-fast" approach uses FastAPI's lifespan event  to guarantee the collection exists before the application accepts any data processing requests, thus eliminating the 404 error class entirely.   

Part 1: Root Cause Analysis: Deconstructing the "Collection Doesn't Exist" Failure
This section meticulously dissects the symptoms to prove that the 404 error is a consequence of a connection and authentication failure, not a bug in Qdrant's collection creation logic.

Section 1.1: The "Smoking Gun": Interpreting the UserWarning
The most critical piece of evidence is the log entry: "Api key is used with unsecure connection". This warning is not issued by Qdrant's server but by the Python qdrant-client library. This warning is documented in multiple issue-tracker reports.   

It is emitted specifically when the QdrantClient is initialized with both:

An api_key argument that is not None.

A connection URL that resolves to http://, or when https=False (the default) is used with the host parameter.   

This warning reveals the exact client-side configuration error. The application is, without a doubt, providing an API key while simultaneously attempting to connect over an unencrypted channel. This is not only a severe security risk (as it leaks credentials in plain text) but, in this case, it is also the trigger for the connection failure.

The logical causal chain is as follows:

The user's logs show the warning.

Therefore, the Python code is passing a non-None value to the api_key parameter of QdrantClient.

And, the application is using a URL that starts with http:// for both local and hosted connections.

This reveals the application is attempting to use a single, flawed configuration for all environments. This static, incorrect configuration is the epicenter of the problem.

The problem is not that ensure_collection() is "failing silently." The problem is that the QdrantClient instance it creates is fundamentally misconfigured and cannot establish a valid, authenticated session with the server to perform any action, including checking if a collection exists.

Section 1.2: The Two-Environment Paradox: Why Local and Hosted Fail Identically
The core confusion in the mission file stems from seeing the same failure on localhost and on the hosted Railway instance. This is counter-intuitive but, given the analysis in Section 1.1, has a clear explanation: in their current state, both servers are default, unauthenticated instances, but the client is always trying (and failing) to authenticate.

Section 1.2.1: Failure Mode 1: Local (localhost:6333)
A standard Qdrant Docker deployment is launched with docker run -p 6333:6333... qdrant/qdrant. The official documentation for this setup is explicit:   

The REST API is accessible at localhost:6333.   

"By default, Qdrant starts with no encryption or authentication".   

Community-corroborated reports confirm this: "if you install qdrant locally on your computer... no API key is installed by default, the database is unsecured by default".   

The failure chain is therefore:

The application, configured with a production API key, attempts to connect to http://localhost:6333.

The qdrant-client library correctly attaches this key as an api-key header to its HTTP request.

The local Qdrant server, which is unauthenticated, receives a request with an api-key header.

Because the server was not configured to expect a key (i.e., QDRANT__SERVICE__API_KEY was not set ), it rejects this request, likely with a 401 Unauthorized or 400 Bad Request.   

The qdrant-client library receives this HTTP error and raises it as an ApiException  or a connection error.   

Section 1.2.2: Failure Mode 2: Hosted (Railway - qdrant-production-1e32.up.railway.app)
Railway is a platform for deploying services, including standard Docker containers. This means that deploying the qdrant/qdrant image to Railway, without additional configuration, results in the exact same default, unauthenticated instance as the local Docker container.   

To enable authentication on any self-hosted Docker-based Qdrant instance (which includes Railway), one must configure the Qdrant server itself. This is done by setting the QDRANT__SERVICE__API_KEY environment variable on the Qdrant service's container.   

The user has almost certainly not done this. They have likely set QDRANT_API_KEY on their application service, but not set the corresponding QDRANT__SERVICE__API_KEY on the Qdrant service.

Therefore, the hosted failure chain is identical to the local one:

The application, configured with its production API key, attempts to connect to the Qdrant instance (incorrectly, via http://...).

The qdrant-client attaches the api-key header.

The Qdrant server on Railway, being a default unauthenticated instance, receives the request with an api-key header it was not configured to expect.

The server rejects the connection.

The UserWarning about the "unsecure connection" is a symptom of this misconfiguration, but the failure itself is one of authentication. Even if the user fixed the URL to https://, the authentication rejection would still occur because the server-side configuration is missing.

Section 1.3: The ensure_collection() Fallacy: It's Not Failing Silently, It's Failing to Connect
The user's ensure_collection() function, presumably a custom wrapper, is not the point of failure. The qdrant-client library provides standard methods like create_collection  and the idempotent pattern if not client.collection_exists(...).   

Any of these methods, including the ensure_collection() wrapper, must first instantiate the QdrantClient. It is this initialization, or the very first API call made with this client (e.g., client.collection_exists()), that is failing due to the client/server authentication mismatch.

This initial failure would raise a qdrant_client.http.models.ApiException  or a base httpx.ConnectError. The application code in ensure_collection() or the admin.py endpoint must be swallowing this critical exception with a broad try...except Exception: block, which then logs the error (or simply passes) and returns.   

This makes it appear that the function "ran" but "did not work." In reality, the function failed to connect, and the collection was never created.

The subsequent upsert_chunks() function fails later with a 404 Not Found. This is not an error; it is an accurate report that the collection does not exist, because the prerequisite ensure_collection() step failed its connection and never completed its task.

Part 2: Correcting Qdrant Client Initialization: A Prescriptive Guide
The solution requires two distinct sets of corrections: first, securing the Qdrant server on Railway, and second, making the application's client configuration environment-aware.

Section 2.1: Step 1 (Server): Securing the Hosted Qdrant Instance on Railway
The production Qdrant instance on Railway must be secured. It is currently unauthenticated, which is a significant security risk.

Actionable Guide:

Navigate to the Railway project dashboard.

Select the Qdrant service (the service running the qdrant/qdrant Docker image).

Click on the "Variables" tab for this service.

Add a new environment variable. This variable is for the Qdrant server itself, not the application.

Name: QDRANT__SERVICE__API_KEY

Value: your-new-secret-api-key (This should be a securely generated, high-entropy string).

Railway will automatically redeploy the Qdrant service with this new variable.

Per the Qdrant security documentation, setting QDRANT__SERVICE__API_KEY (or service.api_key in a config file) enables API key authentication. All subsequent requests to this server must include a matching api-key header to be accepted.   

Section 2.2: Step 2 (Client): Environment-Aware Configuration in the Application
The application must stop using a single, static configuration and instead load its Qdrant settings from environment variables. This allows the same application code to connect to different Qdrant instances (local vs. production).

The qdrant-client library is designed for this. The QdrantClient constructor accepts url and api_key parameters. These can be populated from the environment.   

The url parameter is the most robust initialization method , as it explicitly defines the protocol (http:// or https://), the host, and the port in a single string. This directly solves the problem of the client attempting to use http:// for the Railway instance. The correct QDRANT_URL for Railway must start with https://.

Part 3: Proof-of-Concept: Verifiable Collection Creation
The following standalone scripts and commands can be used to test and validate the new configuration, isolating the process from the main application.

Section 3.1: PoC 1: Python Script (Idempotent Creation)
This script (R7.1_poc_create_collection.py) serves as a working proof-of-concept. It correctly connects to Qdrant based on environment variables and idempotently ensures the collection exists.

Python
import os
import sys
from qdrant_client import QdrantClient, models
from qdrant_client.http.models import ApiException
from dotenv import load_dotenv

# --- Configuration ---
# Load.env file for local testing
load_dotenv() 

QDRANT_URL = os.getenv("QDRANT_URL")
QDRANT_API_KEY = os.getenv("QDRANT_API_KEY")

COLLECTION_NAME = "research_chunks"
# CRITICAL: This must match your embedding model's output dimension
# e.g., 768 for 'all-MiniLM-L6-v2' or 1536 for 'text-embedding-ada-002'
VECTOR_DIMENSION = 768 
# --- End Configuration ---

if not QDRANT_URL:
    print("ERROR: QDRANT_URL environment variable is not set.", file=sys.stderr)
    sys.exit(1)

print(f"Attempting to connect to Qdrant at: {QDRANT_URL}")

try:
    # Initialize the client
    # Set a reasonable timeout for connection attempts
    client = QdrantClient(url=QDRANT_URL, api_key=QDRANT_API_KEY, timeout=20)
    
    print("Client initialized. Checking for collection...")

    # Idempotent creation logic, as recommended by Qdrant docs 
    if not client.collection_exists(collection_name=COLLECTION_NAME):
        print(f"Collection '{COLLECTION_NAME}' does not exist. Creating...")
        
        # Use client.recreate_collection for simple, idempotent creation
        # This will create or update the collection to match the config
        client.recreate_collection(
            collection_name=COLLECTION_NAME,
            vectors_config=models.VectorParams(
                size=VECTOR_DIMENSION,
                distance=models.Distance.COSINE
            ),
        )
        print(f"Collection '{COLLECTION_NAME}' created successfully.")
    else:
        print(f"Collection '{COLLECTION_NAME}' already exists.")

    # Verify by listing collections
    collections = client.get_collections()
    print("\nVerification: Available collections:")
    print(collections)
    
    if COLLECTION_NAME not in [c.name for c in collections.collections]:
        print("\nERROR: Collection creation reported success, but not found in list.")
    else:
        print("\nSUCCESS: Collection is present and ready.")

except ApiException as e:
    print(f"\n--- QDRANT API ERROR ---", file=sys.stderr)
    print(f"HTTP Status Code: {e.status_code}", file=sys.stderr)
    print(f"Error Details: {e.content}", file=sys.stderr)
    if e.status_code == 401:
        print("\nTROUBLESHOOTING (401 Unauthorized):", file=sys.stderr)
        print("1. Is your QDRANT_API_KEY correct?", file=sys.stderr)
        print("2. Did you set QDRANT__SERVICE__API_KEY on the Railway Qdrant *service*?", file=sys.stderr)
except Exception as e:
    print(f"\n--- GENERIC ERROR ---", file=sys.stderr)
    print(f"An error occurred: {e}", file=sys.stderr)
    print("\nTROUBLESHOOTING:", file=sys.stderr)
    print("1. Is the QDRANT_URL correct? (e.g., https://... for Railway, http://... for local)", file=sys.stderr)
    print("2. Is the local Docker container running (if testing locally)?", file=sys.stderr)
    print("3. Is the Railway service healthy?", file=sys.stderr)

Part 4: Best Practices for Collection Lifecycle Management
This section definitively addresses the mission question: "Should collection be created at startup vs on-demand?" The recommended approach is on application startup.

Section 4.1: Analysis of Collection Creation Strategies
Strategy 1: On-Demand (Via Admin Endpoint)
This is the current, failing approach (an endpoint in app/api/v1/admin.py).

Pros: The application can start without a valid Qdrant connection, potentially reporting "degraded" status.

Cons:

Race Conditions: This is the most significant flaw. If the application is scaled to multiple workers (e.S_G., with Gunicorn) and multiple processing jobs arrive simultaneously, all workers may check collection_exists (result: False) and then all attempt create_collection. This will result in errors for all but one worker.

Latency: The first user to trigger this endpoint, or the first processing job, pays the "tax" of collection creation, leading to a slow first request.

Hidden Failures: As demonstrated by this mission, a persistent connection failure in this on-demand logic is masked. The application appears to be running, but it is in a broken state, failing requests with 404 or 500 errors downstream.

Strategy 2: Manual (One-time Script)
This involves an operator running the PoC script (Part 3.1) or curl (Part 3.2) once for each environment.

Pros: Simple, decouples infrastructure from application code.

Cons:

Breaks Automation: This is not an automated, repeatable process. It does not follow Infrastructure-as-Code (IaC) principles.   

Prone to Human Error: An operator can forget, or a new environment (e.S_G., "staging") can be provisioned and miss this step.

Does Not Validate: The application still has no guarantee the collection is there, so it cannot "fail-fast" if the collection is accidentally deleted.

Strategy 3: On Application Startup (Recommended Best Practice)
This is the "fail-fast" approach. The application proves it can connect to Qdrant and ensures the collection exists before it finishes starting up and accepts any web requests.

Pros:

Fail-Fast: If Qdrant is misconfigured (wrong URL/key) or down, the application will not start. This is a critical and desirable feature. It immediately signals a broken deployment to the CI/CD pipeline and Railway, rather than silently running and failing user requests.

Guaranteed Readiness: The upsert_chunks() function will never be called unless the collection has already been confirmed to exist. This completely eliminates the 404 Not Found error class.

Idempotent & Simple: The check runs every time the app starts, ensuring consistency and handling race conditions (as only one startup event occurs).

Section 4.2: Implementation Guide: FastAPI lifespan Events
The correct, modern method for handling startup/shutdown tasks in FastAPI is the lifespan context manager. The older @app.on_event("startup") syntax is deprecated.   

The lifespan function is the perfect, centralized location for all infrastructure readiness checks (Qdrant, databases, etc.).

Code (app/main.py):

Python
import os
from contextlib import asynccontextmanager
from fastapi import FastAPI
from qdrant_client import QdrantClient, models
from qdrant_client.http.models import ApiException

# --- Lifespan Context Manager ---
@asynccontextmanager
async def lifespan(app: FastAPI):
    # ==========================
    # == STARTUP LOGIC ==
    # ==========================
    print("Application starting up...")
    
    QDRANT_URL = os.getenv("QDRANT_URL")
    QDRANT_API_KEY = os.getenv("QDRANT_API_KEY")
    COLLECTION_NAME = "research_chunks"
    # Ensure this matches the model dimension
    VECTOR_DIMENSION = 768 

    if not QDRANT_URL:
        print("--- CRITICAL STARTUP ERROR ---")
        print("QDRANT_URL is not set. Application cannot start.")
        raise ValueError("QDRANT_URL is not set.")

    print(f"Connecting to Qdrant at {QDRANT_URL}...")
    
    try:
        # Initialize a single, reusable client if desired
        # Or, initialize here just for the check
        client = QdrantClient(url=QDRANT_URL, api_key=QDRANT_API_KEY, timeout=30)
        
        # Prove connection and check/create collection
        if not client.collection_exists(collection_name=COLLECTION_NAME):
            print(f"Collection '{COLLECTION_NAME}' not found. Creating...")
            client.recreate_collection(
                collection_name=COLLECTION_NAME,
                vectors_config=models.VectorParams(
                    size=VECTOR_DIMENSION,
                    distance=models.Distance.COSINE
                )
            )
            print(f"Collection '{COLLECTION_NAME}' created.")
        else:
            print(f"Collection '{COLLECTION_NAME}' already exists. All good.")
        
        # Optional: Store the client in app.state for reuse in endpoints
        app.state.qdrant_client = client
        print("Qdrant client initialized and collection is ready.")

    except ApiException as e:
        print(f"--- CRITICAL STARTUP ERROR (API) ---")
        print(f"Failed to initialize Qdrant. Application will not start.")
        print(f"Status Code: {e.status_code}")
        print(f"Details: {e.content}")
        # Re-raise the exception to stop the application from starting
        raise e
    except Exception as e:
        print(f"--- CRITICAL STARTUP ERROR (Generic) ---")
        print(f"Failed to initialize Qdrant. Application will not start.")
        print(f"Error: {e}")
        # Re-raise the exception to stop the application from starting
        raise e

    yield # <--- The application is now running and accepting requests --->
    
    # ==========================
    # == SHUTDOWN LOGIC ==
    # ==========================
    print("Application shutting down...")
    if hasattr(app.state, 'qdrant_client'):
        app.state.qdrant_client.close()
        print("Qdrant client closed.")

# --- FastAPI App Initialization ---
app = FastAPI(
    title="CMOS API",
    lifespan=lifespan  # Pass the lifespan manager to the app
)

#... include your routers (e.g., from admin.py, etc.)...
#
# N.B.: The admin endpoint for creating the collection is no longer needed
# and can be safely removed.
#
By adopting this pattern, the application becomes robust. The admin.py endpoint is now redundant, and any service (qdrant_service.py) can safely assume the collection exists.

Setup Guide: Qdrant with Railway and Local Docker
This guide provides the end-to-end steps for setting up Qdrant for both local development and a secured production environment on Railway.

1. Local Development Setup (Docker)

For local development, we will run Qdrant using the official Docker image. It will be unauthenticated for simplicity.

Pull the Image:

Bash
docker pull qdrant/qdrant
Run the Container:

Bash
docker run -p 6333:6333 -p 6334:6334 \
  -v "$(pwd)/qdrant_storage:/qdrant/storage:z" \
  qdrant/qdrant
This command, sourced from the Qdrant Quickstart , maps the REST API port (6333) and gRPC port (6334).   

It also mounts a local directory (./qdrant_storage) into the container at /qdrant/storage for persistent data. Your vector data will survive container restarts.

Local Environment Variables: Create a .env file in your application's root directory for local development:

QDRANT_URL=http://localhost:6333
# QDRANT_API_KEY is intentionally left unset
The default local instance has no authentication. Your application code (from Part 2.4) will read QDRANT_API_KEY=None and correctly connect without authentication.   

2. Production Setup (Railway)

For production, we will deploy Qdrant on Railway and enable authentication. This is a two-step process: securing the Qdrant service, then configuring the application to connect to it.

Step 2.1: Deploy and Secure the Qdrant Service

Deploy Qdrant:

In your Railway project, add a new service.

Select "Deploy from Docker Image" and use the official image name: qdrant/qdrant.

Go to the new Qdrant service's "Settings" tab in Railway.

Add a Volume. Set the Mount Path to /qdrant/storage. This is non-negotiable for production and ensures your vector data persists across redeploys.

Enable Authentication (Critical Step):

Go to the Qdrant service's "Variables" tab.

Add the following environment variable to the Qdrant service:

Name: QDRANT__SERVICE__API_KEY

Value: `` (Use a password generator. Store this key securely.)

This variable (documented in ) tells the Qdrant server to lock itself and require this key for all API requests. The service will redeploy.

3. Application Code

Your Python application, using the environment-aware initialization (Part 2.4) and the FastAPI lifespan event (Part 4.2), will now behave correctly in both environments:
