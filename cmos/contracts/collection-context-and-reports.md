# Collection context and report citations (UX-8)

Guiding plan: [UX overhaul roadmap](../foundational-docs/roadmap-sprints-50-53-ux-overhaul.md). Composition follows the [OODS object mapping](oods-object-model.md), interaction follows [frontend hygiene](frontend-hygiene.md), and seed authoring follows the [mission boundary contract](mission-authoring-contract.md#collection-context-seed-ux-8-2026-09-13).

Collections retain their name, description and excerpt membership, and add nullable instructions (maximum 20,000 characters). Migration 046 adds `collections.instructions` and a separate `collection_documents` join table with cascading foreign keys. Direct membership supports source documents before processing; it does not manufacture chunks or relax the existing 100-excerpt collection limit.

Authenticated `/collections/{id}/documents` supports GET (page, page_size up to 100), POST (`document_id`, idempotent), and DELETE `/{document_id}`. Context is the distinct union of direct documents and documents referenced by saved excerpts. Both document and parent project must be readable and non-deleted. Authorization precedes counting, paging and writes. Removing a document detaches both forms of membership without deleting the document or its chunks. SQLite and PostgreSQL use their native conflict-safe insert; upgrade, downgrade and cascade behavior are covered against real PostgreSQL.

The read-only `/collections/{id}/mission-seed` response includes all readable context documents, independently of the document-list page. Instructions and source identities populate existing background, structured references and context fields; one source project is preselected, while mixed or empty context requires a project choice. `/missions/new?collection={id}` reviews those inputs before the existing save, contract-preview and submit lifecycle. References record provenance; they do not impose an additional worker access boundary. Reference edits preserve the exact row identity and structured metadata, including when source documents share a filename. No MCP schema or worker SELECT field changes.

The collection picker uses the shared mounted Dialog, complete server collection totals, and either document or excerpt attachment. If creation succeeds but attachment fails, retry uses the same collection. Collection detail edits instructions and exposes document paging, removal, mission seeding and the existing excerpt/report/export controls. Existing routes remain canonical; the new authoring query is not a route migration.

RBAC-enabled collection detail, count, export and excerpt addition enforce the document policy as well as project scope. Report creation resolves that same readable subset before synthesis/cache use and persists only effective synthesis sources. Explicit flag-off/internal legacy service calls retain their prior optional-argument behavior. No role or Space policy is changed.

Reports use server totals and status/project filters. Citation destinations come only from the existing scoped Evidence API with `report_id`: persisted ledger entry sources, independently readable result missions, and literal HTTP(S) citations in report content. Counts and pagination apply after that relationship filter and the existing evidence policy. A raw ReportSource identifier is not a permission grant. Project owners and Space members retain their existing evidence access; unrelated cross-project source records cannot expand it.

Markdown, JSON and text export content bytes are unchanged. Download headers now supply an ASCII fallback and UTF-8 filename for titles that previously produced invalid headers. Tests preserve Unicode content, citation URLs and whitespace. Report creation keeps the mounted shared Dialog and restores focus on dismissal.

Validation includes >100 distinct context documents, revoked/hidden/deleted source checks, complete authoring references through the actual MCP client handler, all citation relationship paths and outside-Space denial, export byte fixtures, full frontend units and built-browser flows in Light/Dark at 390/820/1440. Deployment and production acceptance evidence belongs in `../reports/sprint-51/ux-8-validation.json`.
