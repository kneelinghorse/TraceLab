# Project bundles and document workflows (UX-7)

Guiding plan: [UX overhaul roadmap](../foundational-docs/roadmap-sprints-50-53-ux-overhaul.md). Presentation follows the [OODS object mapping](oods-object-model.md); shared interaction rules are in [frontend hygiene](frontend-hygiene.md). [Home's contract](home-api.md) owns favorite persistence and pagination.

Projects keep their existing URLs. The hub accepts `?tab=Overview|Documents|Evidence|Collections|Missions|Reports`. Each resource tab uses its existing REST endpoint with a project filter and server pagination. Overview reads `/projects/{uuid}/stats`, whose document, chunk, token, report and update-time aggregates now apply the same child policies as the corresponding list endpoints. Scoped statistics bypass the metadata cache so revocation takes effect immediately. Document upload, process, delete and restore invalidate the project's metadata cache as well as document lists.

`GET /collections` accepts optional `project_id`, `page` (default 1) and `page_size` (maximum 100). Supplying paging or project scope returns the same `{data,total}` envelope over a server page. A project collection is one containing readable chunks from non-deleted documents in that project; this does not create project ownership of a collection. The relationship filter and collection RBAC apply before count and pagination. `item_count` in this response counts the readable chunks in the requested scope. Missing or inaccessible project filters return 404. Omitting every new option preserves the legacy complete collection response used by existing MCP clients.

`DocumentUpload` is shared by project Documents and `/documents/upload`; the latter accepts a `project_id` preselection from the full accessible project list. Each selected file keeps its own state and result. Browser upload events supply transfer progress only, and unknown transfer totals remain indeterminate. A file is uploaded only after a successful server response returns its document ID. Processing follows separately; failed stages remain visible even when the outer pipeline reports completed. Retrying a processing failure uses that saved document ID without repeating the upload. A failure on one file does not stop the remaining files. The upload endpoint authorizes its non-deleted project before writing any bytes to storage.

Document list/detail use the [document status projection](oods-object-model.md#projection-rules). Absent processing booleans remain unknown; older failures cannot supersede a newer successful event. Offset-free database timestamps are displayed as UTC. Chunks stay inline in Document, with server totals, content, source offsets and AddToCollection retained. The Evidence tab uses the existing `document_id` evidence relationship filter. Download, processing, editing, deletion and recovery semantics remain on their existing endpoints. No new Chunk URL or MCP authoring field is introduced.
