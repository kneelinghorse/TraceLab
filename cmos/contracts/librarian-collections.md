# Reviewed collections (ORG-1)

Decisions #555/#556 implement the [Sprint 60 handoff](../planning/sprint-60-HANDOFF.md), guided by the [roadmap template](../foundational-docs/roadmap_template.md) and [architecture template](../foundational-docs/tech_arch_template.md). Existing collection context and reports follow [their shared contract](collection-context-and-reports.md).

`POST /librarian/collections/draft` requires a human caller, a readable live selected project and a 1–4,000-character goal. The project predicate and current document read policy apply before sampling for every role. Read at most 20 non-empty chunks of at most 4,000 characters each and at most 24,000 total characters, ordered by document identity/chunk index/identity. Report readable/eligible/used chunk and document counts, exclusions and limits. Documents without eligible saved chunks are not analysed or called whole-document evidence. No retrieval, embedding or fabricated chunks are involved.

One configured Librarian JSON call, capped at 4,000 output tokens, returns one to four groups with names (255 characters), purpose descriptions (2,000 characters), cited rationales (2,000 characters) and one to twenty unique supplied markers in reading order. Shared report coverage and source validators reject unsupported markers, uncited rationales, changed text or lost access. Paid refusals, malformed output and truncation count against the caller/project; there is no automatic repair. Drafting writes usage only, never research artifacts.

Each group receives a seven-day signed token, bound to its own audience, caller, selected project, stable collection UUID, ordered source hashes, goal, model, generation time, generated metadata and destination. The existing collection destination rule is preserved: caller ownership and `default_workspace_id(db)`, shown by name before acceptance. Source project context does not change Space membership or sharing grants.

`POST /librarian/collections/accept` accepts only project, signed token, reviewed name/description and a non-empty ordered subset of the group's chunk IDs. Its schema explicitly caps membership at the existing 100-excerpt limit; the proposal itself is smaller. Extra provenance/ownership/action fields are forbidden. Current project/source identity, hash, access and liveness are checked before creation, within each existing `CollectionService.add_chunk` transaction and before final completion. The request session releases its validation locks before calling the service's independent transactions.

Migration 055 adds nullable collection `generation_provenance` and item `review_position`. Provenance retains origin, caller/time, goal/model/project, destination, exact accepted values/member order, source hashes, immutable accepted-payload fingerprint and completion state. A caller/proposal-namespaced receipt in the existing idempotency table commits atomically with creation and survives collection deletion. Retries/concurrent submissions reuse that collection; a changed payload or deleted accepted artifact cannot silently recreate it. Partial responses identify completed/missing members. Completed retries never refill later manual removals. Each accepted group is independent; dismissing or generating another proposal creates nothing.

Reviewed positions lead collection detail, export and report/synthesis input ordering. Legacy null positions retain each existing path's addition-time ordering; no historical reordering/backfill occurs. Manually appended unpositioned items follow reviewed members. A pending collection changed outside acceptance must be reviewed directly. Existing collection views expose a boolean origin marker; `GET /librarian/collections/{id}` returns its origin and currently readable source provenance. Unavailable sources have no identity/link/text, and project-specific context is withheld if access is lost.

Browser state is caller/project keyed. Generation/acceptance run only on explicit action, with separate group acceptance and recoverable retry. Existing collections, documents, tags and Space membership are never rewritten. These three assistant operations are REST-only by design; existing MCP collection fields and tools remain unchanged. Actual deployed collection retrieval must preserve the saved member order and source identities.
