# Environment Setup Guide

This document provides a clear reference for TraceLab's local development and Railway production environments, including credentials, database connections, and operational procedures.

## Environment Overview

| Component | Local Development | Railway Production |
|-----------|-------------------|-------------------|
| PostgreSQL | localhost:5433 (Docker) | Railway PostgreSQL addon |
| Qdrant | localhost:6333 (Docker) | Qdrant Cloud (free tier) |
| FastAPI | localhost:8000 | https://api.tracelab.aquex.ai |
| Frontend | localhost:3000 | https://tracelab.aquex.ai |

## Authentication

### Credentials

Both environments use the same auth credentials (stored in `.env`):

```bash
AUTH_USERNAME=<admin-email>
AUTH_PASSWORD=<strong-unique-password>
```

### JWT Tokens (Short-lived)

JWT tokens expire after 24 hours. Use for interactive sessions:

```bash
# Get a JWT token
curl -X POST "http://localhost:8000/api/v1/auth/login" \
  -H "Content-Type: application/json" \
  -d '{"email":"<admin-email>","password":"<strong-unique-password>"}'

# Use in requests
curl -H "Authorization: Bearer <token>" http://localhost:8000/api/v1/projects
```

### API Keys (Long-lived)

For MCP servers and automation, use non-expiring API keys:

```bash
# Create an API key (requires JWT auth first)
curl -X POST "http://localhost:8000/api/v1/auth/api-keys" \
  -H "Authorization: Bearer <jwt_token>" \
  -H "Content-Type: application/json" \
  -d '{"name": "MCP Server Local"}'
```

API keys use the `X-API-Key` header:

```bash
curl -H "X-API-Key: tl_xxxxx" http://localhost:8000/api/v1/projects
```

**Current API Keys:**

### MCP Server Configuration

For Claude Code MCP integration, use the appropriate API key based on environment:

**Local Development:**
```json
{
  "mcpServers": {
    "tracelab": {
      "command": "npx",
      "args": ["-y", "@aquex/tracelab-mcp"],
      "env": {
        "TRACELAB_API_URL": "http://localhost:8000",
        "TRACELAB_API_KEY": "<local-api-key>"
      }
    }
  }
}
```

**Production:**
```json
{
  "mcpServers": {
    "tracelab": {
      "command": "npx",
      "args": ["-y", "@aquex/tracelab-mcp"],
      "env": {
        "TRACELAB_API_URL": "https://api.tracelab.aquex.ai",
        "TRACELAB_API_KEY": "<production-api-key>"
      }
    }
  }
}
```

`TRACELAB_API_URL` is an origin, not an API-prefix URL. The MCP package
appends `/api/v1` to its request paths.

Or if using headers directly:

```bash
# Local
curl -H "X-API-Key: <local-api-key>" http://localhost:8000/api/v1/projects

# Production
curl -H "X-API-Key: <production-api-key>" https://api.tracelab.aquex.ai/api/v1/projects
```

## Database Connections

### Local PostgreSQL (Docker)

```bash
# Connection string
postgresql://postgres:postgres@localhost:5433/tracelab

# Direct access
psql -h localhost -p 5433 -U postgres -d tracelab
```

### Railway PostgreSQL (Production)

Connection details are in `.env` under `DATABASE_URL`. To connect directly:

```bash
# Using Railway CLI
railway connect postgres

# Or using psql with the connection string from Railway dashboard
psql "$DATABASE_URL"
```

**Important:** The production database connection string is in `.env`. Keep this file secure and never commit it.

## Qdrant Vector Database

### Local Qdrant (Docker)

- URL: `http://localhost:6333`
- Dashboard: `http://localhost:6333/dashboard`
- No authentication required locally

### Qdrant Cloud (Production)

- URL: Configured in `.env` as `QDRANT_URL`
- API Key: Configured in `.env` as `QDRANT_API_KEY`
- Collection: `research_chunks`

## Database Migrations

### Running Migrations

```bash
# Local (from project root)
alembic upgrade head

# Production (via Railway)
# Migrations run automatically on deploy, or manually:
railway run alembic upgrade head
```

### Schema Recovery

If the production database schema gets corrupted:

```bash
# Connect to Railway PostgreSQL
railway connect postgres

# Nuclear option - drop and recreate (DESTROYS ALL DATA)
DROP SCHEMA public CASCADE;
CREATE SCHEMA public;
\q

# Re-run all migrations
railway run alembic upgrade head
```

## Backup Strategy

### PostgreSQL Backups

Production PostgreSQL is backed up regularly using Railway's backup features or manual dumps:

```bash
# Manual backup
pg_dump "$DATABASE_URL" > backup_$(date +%Y%m%d_%H%M%S).sql

# Restore from backup
psql "$DATABASE_URL" < backup_20251207_120000.sql
```

**Backup Location:** Store backups securely outside the repository.

### Qdrant Backups

Qdrant Cloud free tier does not support backups. However:

- Vector data can be regenerated by re-processing documents
- The `research_chunks` collection is recreated via `/api/v1/admin/init-qdrant`
- Semantic cache (`semantic_cache` collection) can be safely deleted and rebuilt

## Common Issues and Recovery

### Issue: "Failed to fetch" / API errors after DB changes

**Cause:** Schema mismatch between Alembic migrations and actual tables.

**Fix:**
1. Check current Alembic version: `alembic current`
2. Compare with actual tables in database
3. If mismatched, drop schema and re-run migrations (see Schema Recovery above)

### Issue: Stale semantic cache causing search errors

**Cause:** Cached entries missing required fields after schema changes.

**Fix:**
```python
from qdrant_client import QdrantClient
client = QdrantClient(url="...", api_key="...")
client.delete_collection("semantic_cache")
```

### Issue: Documents not embedding

**Cause:** Documents smaller than `min_chunk_size` (500 tokens / ~2KB) produce zero chunks.

**Fix:** Use larger documents for testing, or adjust chunking config in `app/services/chunking.py`.

### Issue: quality_scoring.py errors

**Cause:** Mission model columns changed (`quality_gates` and `mission_data` no longer exist).

**Fix:** Updated to use `mission_metadata` and `execution_metadata` (fixed in commit d41a686).

## Deployment Checklist

Before deploying to Railway:

1. [ ] Run `alembic upgrade head` locally to verify migrations
2. [ ] Run `npm run type-check` in frontend
3. [ ] Test locally with production-like data
4. [ ] Commit all changes
5. [ ] Push to trigger Railway auto-deploy
6. [ ] Verify `/api/v1/admin/health` after deploy
7. [ ] Test key flows (auth, projects, documents, search)
